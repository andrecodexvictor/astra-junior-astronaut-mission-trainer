# ASTRA: world and Babylon architecture

**Status: architecture proposal plus research. A smaller independent demo is now implemented; see HANDOFF.md and TEST_REPORT.md for the actual boundaries and tests. Browser/GPU testing remains pending.** Research began 2026-11-13 and was checked again 2026-11-14 in America/Sao_Paulo. The owner has selected an independent disposable demo, so local development may continue. Competition rules apply separately to any future official entry. The goal is an original lunar exploration game with Pokémon-like readable traversal, discoveries and companion relationships, not copied characters, names, music, art or mechanics. The science simulation remains the authority for life support and tradeoffs. Reference IDs link to the primary-source record in [BABYLON_REFERENCES.json](research/BABYLON_REFERENCES.json).

## Existing prototype and migration boundary

The local `/workspace/sites/astra-lunar` README describes a static Babylon.js 9.35 site, not a minimal Three.js app: eight local GLBs, six compact zones, a 17-scene visual-novel layer, a lunar base and a pure simulation module. It describes NullEngine and Khronos validation, but explicitly says real GPU Chrome QA was unavailable. `dist/game.js` is a large scene and gameplay orchestrator; separate simulation, quests, locomotion and world files already exist. The render loop accumulates frame time and calls the simulation; `simulation.js` preserves subsecond remainder and internally steps whole seconds. Do not call the existing work fresh hackathon implementation. Preserve its tests and provenance as evaluation material; eligibility and any reuse decision belong to the competition rules, not this document.

Pivot the experience toward a small explorable landing region, one companion, and a consequential science loop: leave the habitat, inspect an ice site with the companion, choose a resource action, return and observe water, energy and oxygen effects. Brief contextual dialogue and field notes support play; long VN scenes do not gate traversal. Start with one complete loop instead of promising an open world, multiplayer or unrestricted collecting.

## Proposed application boundaries

Use Vite + TypeScript and pinned, compatible modular `@babylonjs/core` and `@babylonjs/loaders` packages [1]. Register the glTF loader explicitly; keep Babylon and loaders at matching versions. Build and host local artifacts with an asset base path that works from the deployed subdirectory. No CDN is required at runtime. Proposed boundaries:

```text
src/app/          boot, engine selection, render loop, settings, save migration
src/world/        region manifest, streamer, terrain, lighting, interactions
src/actors/       player, companion, movement, animation and camera
src/simulation/   pure state, one-second tick, units, actions, seeded events, replay
src/presentation/ HUD, map, accessible DOM controls, journal and localized text
src/assets/       typed asset registry, preload and disposal
public/assets/    versioned GLBs, textures, terrain tiles, audio and licenses
```

Dependencies point inward: simulation knows no Babylon, wall clock, DOM or asset paths. Commands enter simulation at a numbered tick; immutable snapshots and explicit events drive presentation. Actor motion and camera can be visually interpolated but cannot silently adjust resource state. Region transitions preserve simulation state, companion relationship and mission progress. Use a stable save schema with version, deterministic seed, tick number, action log and any accumulator remainder; validate inputs, migrations and corrupted saves. A fresh start and a safe recovery path are required.

## Time, science and replay

A monotonic scheduler accumulates **real elapsed time × explicit acceleration** and consumes it in exact `tick(state, 1)` calls. Acceleration is a visible, named setting, saved and logged as a tick-boundary command. Define pause, menu, hidden tab, reload and excessive backlog policies explicitly: default pause while hidden and while paused; no silent catch-up on resume. Bound work per frame without dropping simulation seconds: leave the remainder in the queue and indicate catch-up, or explicitly pause acceleration. A render-frame clamp may protect camera movement but must not silently change resource time. Rendering interpolates snapshots; frame `delta` never directly changes resources. Display tick/time and acceleration.

Replay starts from a versioned initial state and seed and applies ordered commands at recorded ticks. Assert identical state hashes at checkpoint ticks for different render frame schedules, pauses and speeds; deterministic PRNG state and event ordering must also be captured. Record numerical units and model assumptions alongside values. State conservation and rates should follow the science documentation and cite actual NASA data; distinguish simplified game models from measured lunar conditions. Any uncertainty or source limitations are visible in the journal. Preserve and run existing simulation tests if permitted to reuse legacy code, then add scenarios for full replay, variable frame rate, queued actions, save/reload and visibility transitions.

## Regions, movement and companion

Choose finite authored regions with clearly signposted portals: habitat/base, ice prospect and greenhouse interior. Region manifests define bounds, terrain/GLB URIs and hashes, spawn/exit points, collision data, interactables, music, light settings, LOD and neighbor preload. The loader prefetches the next adjacent region during a transition, instantiates it only when ready, and disposes owned nodes, animation groups, textures and observers when no longer referenced; shared assets use reference counts. On failure retain the old region and offer retry. Persist IDs and state, not Babylon nodes. Test repeated transitions for stable memory. A region can start as a small subdivided ground mesh; if terrain grows, stream bounded heightfield tiles, with seam-consistent sampling, normals and collision at matching coordinates. There is no claim of an infinite world or physically accurate full Moon.

Start with Babylon's built-in `moveWithCollisions` and a simple capsule/ellipsoid-shaped player collider, authored static collision hulls, grounded checks and constrained lunar-gravity jump. This matches a small, largely kinematic game and avoids physics runtime overhead. The Physics V2 `PhysicsCharacterController` [4] is a separate path and needs the physics plugin; its shape casts, slopes and moving-platform handling are useful if a tested playable slice demonstrates a need. If selected, use Havok through Babylon's plugin [5], pinned npm package plus locally served WASM, explicit asynchronous initialization, WebAssembly SIMD support check, and an understandable failure or built-in-collision fallback. Havok has its own MIT license, distinct from Babylon's Apache 2.0; verify the shipped package's license and include both notices. Test WASM MIME, base paths, no-network operation after local assets are present, and unsupported-device behavior. Do not pretend both controllers have identical physics or replay behavior. Neither render collision nor Havok contact outcomes define the authoritative life-support simulation.

Companion: use a follow/idle/interact state machine with stable IDs and a navigation anchor behind the player; stop at interactions, teleport safely if stranded, and never block required controls. Author the companion's nonverbal cues and reactions without implying scientific observations are validated facts. Use collision sweeps or simple steering and a safe recall interaction; avoid promising general pathfinding in the first slice. Player input supports keyboard, pointer and touch, and the same actions remain reachable in DOM controls.

## Asset and animation pipeline

The asset registry loads local glTF/GLB via `AssetContainer` once per template [2]. Call `instantiateModelsToScene`, retain the returned root nodes, skeletons and **per-instance animation groups**, and dispose those entries on unload; shared materials/textures must outlive their instances. Explicitly choose cloned material only for unique overrides. Test two animated companions simultaneously: changing one clip or disposing one instance must not alter the other. Use in-place idle, walk, run, jump and interact clips driven by movement state; synchronize visual speed to movement and crossfade without giving root motion authority over collision or simulation.

Prefer clips authored against the same rig. For another rig, Babylon 9's `AnimatorAvatar.retargetAnimationGroup` produces a new group [3]. Reset the source hierarchy to its actual rest pose, map names, check hierarchy, choose root/foot reference and inspect missing targets, foot sliding and ground offsets. glTF targets transform nodes; the documented method does not support source groups animating bones directly. Cache approved retargeted results and dispose temporary groups. Live clip changes must be instance-local and tested across transitions; a plausible animation is not evidence of physically correct motion.

Asset intake: retain source files and export settings; apply transforms, scale and consistent axes; export GLB with named clips, predictable rig, PBR materials, bounded texture sizes, LODs and simplified collision hulls. Run Khronos glTF Validator, inspect warnings, load with the pinned Babylon loader, then inspect animation, material and collision in a real browser. Maintain a manifest containing ID, version/hash, author, origin URL, license and attribution, creation date, AI-use disclosure, processing steps, region and dependencies. Confirm redistribution and competition eligibility for every asset, including fonts, audio and generated images; disclose AI tooling when required, do not crop watermarks or assume a generated output is unrestricted. Record NASA data source, date, transformation and caveats separately. Bundle notices with the artifact. No example asset or code is automatically licensed for ASTRA merely because a demo links it.

## Engine, lighting, accessibility and budgets

Attempt WebGPU only after an actual asynchronous support check (`WebGPUEngine.IsSupportedAsync`), then await engine initialization inside a try/catch. On unsupported adapter or initialization failure, dispose any partial engine and create a WebGL **2** engine before constructing scene/resources; verify the created engine actually has WebGL 2, otherwise show a clear unsupported-device screen. Do not claim WebGPU solely because `navigator.gpu` exists. Capability tests must cover both forced paths and failure; do not assume arbitrary scene features match across renderers [6].

Use one authored PBR environment per region and a restrained key light, with baked static lighting or lightmaps where suitable and a small shadow budget for moving actors. Check the Moon's harsh illumination and dark shadows while retaining navigable contrast; artistic fill is labeled as presentation. Enable optional effects only after measurements, and ensure reduced-motion settings suppress camera shake and nonessential transitions. Use accessible HTML overlays for menus, journal and critical actions: semantic labels, focus order and visible focus, keyboard operation, scalable text, meaningful contrast, captions and non-color-only status. Babylon GUI [11] can support in-world markers but is not a substitute for screen-reader semantics. Pause controls never trap focus.

Initial **targets, not measured results**, for a representative midrange laptop at 1080p and mobile at a documented resolution: 60 fps desktop / 30 fps mobile in the demo region; 95th-percentile frame time under 16.7/33.3 ms respectively, excluding explicitly recorded load screens; draw calls under 150 desktop / 100 mobile; initial transfer under 25 MB compressed and peak texture budget under 128 MB on mobile. Set final numbers after baseline profiling on named devices. Measure CPU/GPU frame time where available, draw calls, active meshes, texture memory estimates, loading and repeated-transition memory with Babylon instrumentation/inspector and browser tools; collect 60-second traces on both paths. Tune mesh LOD [7], static thin instances [8] and static-region octrees [9] only after measuring. Thin instances are suited to many similar noninteractive rocks, not independent animated companions; account for coarse batch culling. Use SceneOptimizer [10] only with an explicit, logged allowlist: automatic mesh merging, shadow removal or scaling can break interaction, readability and art. Disable any optimization that changes semantics; offer predictable quality presets.

## Evidence-to-decision matrix

| Feature | Official example or documentation | Applied pattern and decision | Proof / initial budget / pitfall |
|---|---|---|---|
| Modular app | Vite guide [1] | Pinned TS modules, local assets | Clean build on a fresh machine; verify loader registration and deployment base path. |
| Reusable actors | AssetContainer example `#S7E00P#439` linked in [2] | One template, instance-owned skeletons/groups | Two independently animated actors and unload test; do not dispose shared materials early. |
| Clip retarget | Retarget example `#K1QFZD#2` in [3] | Same rig first; explicit mappings otherwise | Walk/run/idle ground contact observed; log missing targets and reset actual rest pose. |
| Collision | Physics V2 controller sample `WO0H1U#165` in [4], Havok [5] | Start built-in collision; evaluate Havok only for demonstrated need | Slope, stairs, doors, moving platforms and fallback on target hardware; test WASM offline. |
| Renderer | WebGPU guide [6] | Feature check + initialized WebGPU or verified WebGL 2 | Run both paths; compare screenshots and interactions; unsupported WebGL 1 is a clear failure. |
| Scenery | LOD sample `#QE7KM` [7], thin instances [8], octrees [9] | Finite streamed tiles; measured static batching/LOD | <150/<100 draw-call target; check LOD popping, batch bounds, stale octrees and seams. |
| Optimization | SceneOptimizer options [10] | Measured allowlist and named quality presets | 60-second trace and no lost interaction or inaccessible text; avoid indiscriminate presets. |
| Real game study | Official Summer Festival repository and guide [12] | Study traversal, character and goal sequencing | Review for ideas, check individual rights; old tutorial code is not a production benchmark. |

Playground IDs above are cited through the official documentation's embedded examples, not represented as tested production applications. The repository URL and documentation endpoints were checked for HTTP accessibility; individual embedded scenes, assets and runtime behavior have **not** been browser-verified in this research.

## Showcases de mundo: source study, not runtime verification

- **Mansion** [13] is an actual Babylon website scene: its loader calls `LoadSceneAsync` for `Mansion.babylon` and enables scene collisions. Inspection of the serialized scene shows fog, one point light, 121 meshes, 57 materials and 28 ambient textures, including files named `VRayLightingMap`; this supports studying authored lighting maps and atmospheric staging, not assuming current PBR or streaming. The serialized file is about 55 MB uncompressed: ASTRA should use smaller regional assets and budget them. The scene was not run, and its art and audio require independent rights review.
- **3D Tiles** [14] is a geographic-world demonstration in BabylonJS/Demos, not a game: its source uses a geospatial camera, `TilesRenderer`, screen-error target, attribution collection, and mobile-specific cache and download/parse queue limits. Apply the lesson of bounded loading, memory and attribution to authored lunar regions; do not copy the external 3D Tiles dependency as a requirement for ASTRA. This example requires a Cesium Ion or Google token and network data and therefore is not an offline implementation template. No runtime performance or visual quality was tested. Pirate Fortress was not located in the checked source tree, so no implementation claims are made about it.

## Handoff and acceptance gates

After event eligibility is confirmed, a new team should deliver a vertical slice in this order: (1) reproduce a permitted baseline or use a clean start only after the eligibility decision, and record asset provenance; (2) isolate simulation and replay contract; (3) build renderer bootstrap and accessible shell; (4) implement one region, player and companion; (5) connect a science interaction and second region with streaming; (6) profile and tune; (7) package credits and replayable build. Parallel work should agree on typed commands, region manifest and save version before integration. Track a short risk register for offline assets, device compatibility and scientific simplifications.

Acceptance requires automated unit/replay and asset-validation checks plus **real browser QA**, not NullEngine alone: Chrome/Chromium WebGL 2 and WebGPU where supported, another target browser and a representative mobile device; keyboard, touch, focus, reduced motion, pause/background/reload and offline behavior; two animated instances, movement/collision and repeated region travel; a complete science loop with units; performance traces against recorded targets; and save/replay state equality across frame schedules. Record device, browser, GPU, screenshots, logs, build revision and known failures. None of these proposed checks were performed for a new implementation in this research.
